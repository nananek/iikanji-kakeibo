# リリースノート

## v5.0.0 — End-to-End 暗号化 (E2EE)

**サーバーが平文を一切持たない構成への全面移行** (Epic [#84](https://github.com/nananek/iikanji-kakeibo/issues/84))。仕訳・証憑画像・医療費などの暗号化／復号はすべて利用者の端末 (ブラウザ / `client-py`) 上で行われ、サーバーには暗号文だけが保存される。

移行手順・利用者がすべきことは **[v4.x → v5.0 移行ガイド]({{ '/v5-e2ee/migration.html' | relative_url }})** を参照。一斉移行の運用スケジュールは E7 ([#114](https://github.com/nananek/iikanji-kakeibo/issues/114)) で告知。

### 暗号化の対象

- **暗号化** — 仕訳の摘要・日付・取引内容、医療費明細 (金額・氏名・病院名等)、証憑画像、AI 下書き画像、残高キャッシュ、バックアップ
- **非暗号化 (サーバーから見える)** — メールアドレス、勘定科目 (コード・名称・区分)、仕訳明細の借方・貸方金額および科目コード (残高集計・損益振替用の平文メタ)、AI 下書きの要約テキスト

### 鍵管理 — マスター鍵 (MK) を 3 認証要素でラップ

- **Passkey** (WebAuthn PRF) / **パスフレーズ** (Argon2id) / **リカバリシード** (BIP-39 24 単語)
- サーバーは MK を保持しない。3 要素をすべて失うとデータは復元不能 (運営者による救済も不可)

### データエクスポート

- **Web**: `設定 → データエクスポート` で復号済み CSV + 証憑画像 + バックアップを zip で直接ダウンロード。メール受け取り (一時保存・有効期限つき) にも対応 (`export_jobs`)
- **`client-py`**: `iikanji export` でローカル完結エクスポート。大規模データ (証憑 200 枚 / 200 MB 超) 推奨
- 退会フローにエクスポート導線を統合 (E2EE 化で退会後の救済は不可能なため)

### client-py の全面 E2EE 化

- 仕訳 / 医療費 / 科目 / 試算表 / P・L / B・S / 元帳 / AI 証憑解析 / 証憑画像 / バックアップ (`.ikbackup`) / 監査連携 (HPKE) を Bearer + ローカル MK で対応
- マスター鍵は OS キーリングに保管。Web 実装と golden vector で byte 一致を検証

### 廃止された機能 (E2EE と非両立)

- **MCP サーバー** (`iikanji-mcp`) — リポジトリ archive 化。代替は `client-py` エクスポート → 手動アップロード
- **Webhook 通知** (Discord 等) — `webhook_configs` / `notify.py` を撤去
- **自家ホスト LLM** (`llama_cpp` プロバイダ) — AI 処理はすべてクライアント側へ移行
- **自動取込** (auto_import) — サーバー側の平文解析を伴うため撤去
- **リアルタイム代理閲覧** (監査者ログイン) — 非同期スナップショット送信に移行 ([#112](https://github.com/nananek/iikanji-kakeibo/issues/112))

### AI 証憑仕訳は継続 (処理経路がクライアント側へ移行)

- ブラウザ / `client-py` 上の orchestrator が利用者の API キーで直接 LLM を呼び出す (OpenAI / Google Gemini / Anthropic Claude / Ollama)
- API キーを含む AI 設定も端末側で暗号化して保存

### 運用者向けデプロイ注意 (損益振替の暗号化移行)

仕訳明細の金額・科目コードをサーバー応答から段階的に除去している ([#338](https://github.com/nananek/iikanji-kakeibo/issues/338))。**過去に決算月3を確定済みの環境では、この除去を含むバージョンをデプロイする前に、各利用者が `設定 → 月次確定` の「すべて再暗号化」を実行**して旧形式の損益振替仕訳 (サーバー生成・未暗号化) を暗号化版へ移行する必要がある (未移行のまま除去版を配ると、確定済み年度の損益振替の金額が表示できなくなる)。`client-py` は新旧サーバー両対応のため、サーバーより先に配布してよい。

## v4.0.0-beta

**一般公開ベータリリース** — セルフホスト前提から「公開 SaaS / 招待制ベータ運用」への大規模拡張。

`BILLING_BACKEND` 環境変数で「セルフホスト全機能解放」「無償ベース機能のみ」「公開 SaaS (将来)」の 3 モードを切替可能。`REGISTRATION_INVITE_ONLY` で招待制ベータを開始できる。

### 公開運用基盤 (Phase 1, 4, 8)

- **法的文書ページ** (`/legal/terms`, `/legal/privacy`, `/legal/tokushoho`) を新設。運営者情報は `OPERATOR_*` 環境変数経由で注入
- **規約再同意フロー** — `CURRENT_TERMS_VERSION` 改訂時に既存ユーザーへ強制再同意を求める
- **お問い合わせフォーム** (`/legal/contact`) — 運営者宛通知 + 送信者宛自動返信、CAPTCHA + レート制限
- **退会フロー** (`/settings/delete-account`) — 全データ削除、Passkey 専用ユーザー対応、電帳法証跡のみ匿名化保持
- **招待トークン制** — `REGISTRATION_INVITE_ONLY=true` で `flask invite-create` で発行したトークン経由のみ登録可能 (email + user_type の二重バインド)

### エンタイトルメント基盤 (Phase 2)

- `BillingClient` 抽象インターフェース + 3 実装 (`UnlimitedBillingClient` / `FreeOnlyBillingClient` / `HttpBillingClient` は Phase 3 で実装)
- `BILLING_BACKEND=free_only` で billing コンテナを立てずに公開ベータ運用可能 (有償機能はすべて拒否)
- 有償機能ゲート: `paid_llm` (自家ホスト LLM) / `voucher_storage` / `audit_seat` / `timestamp_seal`

### ストレージクオータ + 電帳法証跡永続化 (Phase 5)

- 証憑画像の容量を `StorageUsage` テーブルで集計 (`voucher_storage` エンタイトルメント、無償枠 500 MB)
- `INSERT ... ON CONFLICT DO UPDATE` で並行 INSERT を原子化、SAVEPOINT パターン退役
- `create_voucher_from_upload` を単一トランザクション化 (旧 2 段 commit ゾンビバグ解消)
- **Voucher 論理削除化** — 削除後も `voucher_audit_logs` を 7 年保管できるよう row を保持 (electronic preservation)
- `flask storage-audit [--fix]` — file_size NULL backfill + StorageUsage drift 検出 + 修正

### メール配信基盤 (Phase 6)

- `SmtpMailBackend` 実装 (STARTTLS / SSL / none の 3 モード)、依存追加なし (smtplib 標準)
- 通知テンプレート: `contact_received`, `contact_received_admin`, `account_deleted`, `quota_warning`, `terms_update`, `audit_invitation`, `security_alert`, `invitation`
- **容量警告メール自動送信** — 80% / 95% 到達時に通知、70% で状態リセット (ヒステリシス)

### セキュリティ強化

- メールヘッダインジェクション対策 (フォームバリデーション + render サニタイズの多重防御)
- `InvitationToken.mark_used` の TOCTOU を `UPDATE WHERE used_at IS NULL` で原子化
- `record_upload` 例外時の TOCTOU 空振りで他ユーザー計上を誤減算するバグを修正
- CodeQL py/url-redirection / py/stack-trace-exposure 誤検出 2 件をコード書き換えで解消

## v3.12.0

**Ollama サポートを終了し llama.cpp に置き換え (サーバー管理者提供型)**

ローカル LLM サポートを Ollama から llama.cpp (llama-server) に置き換えました。
位置づけも変更: 「ユーザーが自分のPCで建てる」のではなく「**サーバー管理者が任意機能として提供**」する形になります。エンドポイントは環境変数 `LLAMA_CPP_URL` でアプリ全体に注入され、ユーザーは設定画面で「llama.cpp」を選ぶだけで利用可能。

### 主な変更
- **`ollama` プロバイダーを完全削除**。既存 `provider="ollama"` の設定は `/settings/ai` で警告が出て別プロバイダーへの再登録を促されます
- **`llama_cpp` プロバイダーを新設**。エンドポイントは `LLAMA_CPP_URL` 環境変数で指定
- **ユーザー個別 base_url を廃止** — `user_ai_configs.base_url` カラムをマイグレーション 035 で削除
- **提供停止時の誘導** — `LLAMA_CPP_URL` 未設定のサーバーでは llama.cpp 選択肢が UI から消える。既存 `llama_cpp` 設定ユーザーが AI 機能を使うと「サーバー管理者が提供を停止しました。AI 設定画面で別のプロバイダーに変更してください」と案内
- マイグレーション 035: `user_ai_configs.base_url` カラム削除
- pytest 1582 件

### サーバー管理者向け
- llama.cpp を提供したい場合: `LLAMA_CPP_URL=http://llama-server:8080` のような形で docker-compose の env に設定
- 提供したくない場合: 環境変数を未設定にすればユーザー UI から選択肢が消える

### 既存 Ollama ユーザー向け移行
- マイグレーションでデータ書換はしません (DB に `provider="ollama"` が残る)
- AI 設定画面を開くと警告が表示されるので、別プロバイダーに切り替えてください

## v3.11.0

**パスキー専用ログインモード + 非常用リカバリコード**

セキュリティを最大化したいユーザー向けに、パスワードログインを完全に無効化する「パスキー専用モード」を導入。紛失時の救済として 1 回限り使用のリカバリコードを発行し、リカバリログイン後はパスキー再登録とリカバリ再生成まで他操作をブロックする強制復旧フローを実装。

### 新機能

- **パスキー専用モード (オプトイン)** — 設定画面のトグルで有効化。ON 中はパスワードログインが拒否され、パスキー or リカバリコードのみでログイン可能
- **非常用リカバリコード** — `ikr_` プレフィックス + `secrets.token_hex(32)` を SHA-256 でハッシュ化して DB 保存。生コードは生成時に 1 回だけ表示され、その後は再表示不可。オフライン保管（紙等）を推奨
- **強制復旧フロー** — リカバリコードでログイン後、「新パスキー登録」と「新リカバリコード生成」の両方を完了するまで他のページにアクセスできない（`before_request` で `/settings/passkeys` へ強制リダイレクト）。両達成でセッションフラグがクリアされ通常モードへ復帰
- **最後のパスキー保護** — パスキー専用モード中は最後の 1 本を削除できない。422 でブロックしリカバリ再生成 + モード解除を促す
- **`POST /auth/recovery`** — リカバリログイン専用エンドポイント。レートリミット `5/minute`、列挙対策で失敗メッセージ一律
- **設定画面 UI** — トグル、前提条件チェックリスト（パスキー >=1 本 + 有効リカバリコード）、強制復旧バナー、コピー/印刷ボタン付き表示画面
- **ログイン画面に「リカバリコードでログイン」リンク** — `/login` と `/login/auditor` 両方

### 技術詳細

- マイグレーション 034: `users` に 5 カラム追加 (`passkey_only_login`, `recovery_code_hash`, `recovery_code_prefix`, `recovery_code_created_at`, `recovery_code_used_at`)
- 既存ユーザーは `passkey_only_login=False` でデフォルト挙動。**破壊的変更なし**
- API キー / OAuth トークンは独立した認証チャネル。パスキー専用モードの影響を受けない（必要なら個別取消）
- リカバリログインは `remember=False`（pending セッションが長期化しないよう）
- 生コードは `flash()` を使わず `render_template` 直接埋め込み（Cookie 漏洩防止）
- pytest 1578 件、test_recovery_login に 29 ケース追加（モデル 6 + エンドポイント 5 + パスキー専用 8 + 削除ガード 2 + リカバリログイン 5 + ペンディング 4）

### 注意事項 (必読)

- パスキー専用モード ON 中に **パスキーとリカバリコードを両方紛失するとアカウントへ二度とログインできません**。リカバリコードは必ず紙等のオフラインメディアに保管してください。
- リカバリコードを再生成すると旧コードは即時無効化されます

## v3.10.2

**ホットフィックス: 引き落とし仕訳を「カード会社未達」から除外**

- **CSV と同方向の仕訳のみを未達対象とする** — クレカ明細 CSV は出金のみが載るため、毎月の引き落とし仕訳 (CC 未払金を銀行から払う = CC 口座への deposit 方向) を未達として表示するのは不当だった。CSV 行に出現する方向 (withdrawal / deposit) を抽出し、journal_only はその方向の仕訳に限定するよう修正
- 例: CSV が出金のみ → 引き落とし仕訳・返金仕訳は除外。CSV に両方向あれば従来通り両方検出

## v3.10.0

**CSV 照合 UX 改善: 日付ズレ照合・カード会社未達ハイライト・ワンクリック修正動線**

レシート起票主軸の家計簿運用を支えるため、CSV 取込時の照合体験を「検出→可視化→修正」まで一気通貫させた。

### 日付ズレ照合と段階バッジ
- **日付トレランスを ±7 日まで拡大** — クレジットカードの「利用日 vs 計上日」ズレや銀行明細の到着遅延を許容し、自動マッチ率を改善
  - 完全一致 (差 0 日) は緑バッジ「照合済」
  - ±1〜3 日は黄バッジ「日付ズレ +N日」(`bi-calendar-event` アイコン)
  - ±4〜7 日は黄バッジ「要確認 +N日」(`bi-exclamation-triangle` アイコン)
  - 8 日以上は照合対象外 (unmatched)
- **誤マッチ防止の貪欲法マッチング** — 同金額の仕訳が複数候補にあるとき、距離 0 を優先確定するグローバル最適化を導入。「同額の仕訳 1 件 × 2 CSV 行」のケースで完全一致側が必ず勝つ
- **ワンクリック日付スナップ** — 日付ズレ/要確認の matched 行に「日付を CSV に合わせる」ボタン。クリックすると `POST /csv-import/match/snap-date` で仕訳の日付を CSV 日付に UPDATE し、その場で緑バッジに切り替わる (リロード不要)。月次確定済み期間に重なる場合はトーストエラーで拒否
- **照合状態カウンタの細分化** — 「照合済 / 日付ズレ / 要確認 / 複数候補 / 未照合」を独立バッジで表示

### カード会社未達ハイライトと修正動線
