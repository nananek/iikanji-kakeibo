# v4.x → v5.0 移行ガイド — End-to-End 暗号化 (E2EE) への移行

v5.0 (Epic [#84](https://github.com/nananek/iikanji-kakeibo/issues/84)) で、いいかんじ™家計簿は
**End-to-End 暗号化 (E2EE)** に全面移行しました。サーバーは帳簿・証憑画像・医療費などの
**平文を一切持たなくなります**。暗号化・復号はすべてあなたの端末 (ブラウザ / `client-py`) 上で
行われ、サーバーには暗号文しか届きません。

本ガイドは、v4.x を利用してきた方が **何が変わり、何をすればよいか** を把握するためのものです。
監査連携 (税理士・公認会計士との共有) の移行は **[監査連携の移行ガイド](audit-migration.html)** を、
設計の詳細は **[v5.0 E2EE 設計書](index.html)** を参照してください。

> **実装状況 (2026-06)**: E2EE 化の実装は開発ブランチ上で完了しています。稼働中サービスへの
> 一斉移行 (メンテナンスウィンドウ・猶予期間) は E7 ([#114](https://github.com/nananek/iikanji-kakeibo/issues/114)) で別途告知されます。

---

## なぜ E2EE 化するのか

家計簿・帳簿は最も機微な個人情報の一つです。従来はサーバー運営者が技術的には
データの平文を閲覧できる構成でしたが、v5.0 ではその可能性そのものを排除します。
サーバー侵害・内部不正・法的開示要求のいずれが起きても、**鍵を持たないサーバーからは
平文が取り出せない**ことを設計で保証します。

---

## 何が暗号化されるのか

あなたの端末上でマスター鍵 (Master Key, MK) により暗号化され、サーバーには暗号文だけが
保存されます。

| 区分 | 内容 |
|------|------|
| **暗号化される** | 仕訳の摘要・日付・取引内容・**借方/貸方金額および科目コード**、医療費明細 (金額・患者名・病院名・治療内容・支払額・保険補填額)、証憑画像、AI 下書きの画像、残高キャッシュ、バックアップ |
| **暗号化されない (サーバーから見える)** | メールアドレス、勘定科目マスタ (コード・名称・区分)、AI 下書きの要約テキスト |

> **仕訳明細の金額・科目コードも暗号化されます。** `journal_entry_lines` の
> `account_code` / `debit_amount` / `credit_amount` は #338 で**物理削除され**、
> 行の科目・金額は `encrypted_blob` にのみ収録されます。残高集計・損益振替・
> 試算表/損益計算書/貸借対照表はすべてあなたの端末側で復号して計算され、サーバーは
> 「ある科目にいくら計上されたか」すら把握できません (設計書 §4 / §12.3 / §13)。
> 貸借一致・科目存在の検査もクライアント (復号時) + 監査時検査の責務に移っています。
> なお勘定科目**マスタ** (名称・区分) は、ログイン不要の軽量 API
> (`client-py` のレポート集計など) を成立させるため平文で残ります (科目コードと
> 名称の対応表であり、どの科目にいくら計上したかという金額情報は含みません)。

## 鍵の仕組み — ログインパスワードが常用鍵 (#385)

v5 では **ログインパスワードがそのままマスター鍵 (MK) の常用解錠鍵**になります
([#385](https://github.com/nananek/iikanji-kakeibo/issues/385))。パスワードを 1 回入力すると
**ログインと同時に MK が解錠**され、帳簿の暗号化・復号が有効になります。

仕組み (クライアント内で完結):
`master = Argon2id(ログインパスワード, salt)` → HKDF で 2 つに分岐し、
`login_verifier` (サーバ照合用) と `mk_wrap_key` (MK の解錠用) を導出します。
**サーバには `login_verifier` を HMAC した値しか渡らず、パスワード生値も MK も渡りません。**
そのため「パスワードを流用しても受動的なサーバー運営者は MK を導けない」ことが保たれます。

MK は次の要素それぞれでラップして保管され、**どれか一つでも復元できれば** MK を取り戻せます。

1. **ログインパスワード** — 唯一の常用鍵。ログイン = MK 解錠を 1 回の入力で同時に行う
2. **リカバリシード** — BIP-39 24 単語。パスワードを忘れたとき / すべてを失ったときの最後の手段。
   このシードで**パスワードをリセット**することもできます (下記「パスワードリセット」)
3. **Passkey (パスキー)** — 任意の上乗せ。WebAuthn PRF 対応端末で追加できます (無くても困りません)

任意で **TOTP 2 要素認証** を有効化できます (下記「TOTP 2 要素認証」)。

> **重要:** サーバーは MK を持ちません。**パスワードもリカバリシードも (Passkey も) すべて
> 失うと、暗号化されたデータは誰にも (運営者にも) 復元できません。** リカバリシードは必ず
> 紙等のオフラインで保管してください。

> **v4 でパスキー専用モードを使っていた方へ:** パスキー専用モード (パスワードを無効化する設定)
> は v5 で**廃止**されました。全アカウントがパスワードを持ちます。該当アカウントは Passkey /
> リカバリシードでログイン後、パスワードを設定してください (リカバリシードによるリセットで
> 設定できます)。

## 利用者がすべきこと

### 1. 初回ログイン (透過移行)

v5.0 への移行後、**いつものログインパスワードを 1 回入力するだけ**で移行が完了します
(#385 の透過移行)。裏側で次が自動実行されます:

1. パスワードの最終確認 (これまでの認証方式での 1 回限りの検証)
2. パスワードからの MK 解錠鍵の確立 (鍵設定を意識する必要はありません)
3. サーバが一時鍵で暗号化していたデータを、あなたの MK で再暗号化 (進捗バー表示)

移行後は **リカバリシード (24 単語) を必ず控えて**ください (設定 → 暗号鍵管理で確認・発行)。
パスワードを忘れたときの復旧手段はこのシードだけです。Passkey の追加は任意です。

- 一斉移行のスケジュール (メンテナンスウィンドウ・猶予期間) は
  **E7 ([#114](https://github.com/nananek/iikanji-kakeibo/issues/114))** で告知されます

### 2. 必要ならデータをエクスポートしておく

E2EE 化後はサーバー側にデータの平文が残らないため、**鍵を失うと運営者による救済は
できません**。心配な場合は事前に手元へエクスポートできます。

- **Web**: `設定 → データエクスポート` から、復号済みの CSV + 証憑画像 + バックアップを
  zip でダウンロード (端末内で復号して生成)。メールでの受け取り (一時保存・有効期限つき) も可能
- **`client-py`**: `iikanji export` でローカル完結のエクスポート。証憑 200 枚 / 200 MB を超える
  大規模データはこちらを推奨

### 3. 廃止される機能を確認する (下記)

## v5.0 で廃止される機能とその理由

いずれも **「サーバーが平文を持つ」ことを前提とした機能**で、E2EE と本質的に両立しません。

| 廃止機能 | 理由 | 代替 |
|----------|------|------|
| **MCP サーバー** (`iikanji-mcp`) | LLM (Claude Desktop 等) に平文を渡す仕組みで E2EE 非両立。リポジトリは archive 化済 | `client-py` でローカルにエクスポート → 手動でアップロード |
| **Webhook 通知** (Discord 等) | 通知本文の生成にサーバー側で平文を読む必要がある | なし (将来 E2EE 整合的に再設計の可能性) |
| **自家ホスト LLM** (`llama_cpp` プロバイダ) | サーバー側で平文を LLM に渡す経路。E2EE では AI 処理はすべてクライアント側で実行 | クライアント側 AI (下記) |
| **自動取込** (auto_import) | サーバーが平文の明細を解析・自動仕訳する仕組み | CSV / OFX / Web 貼り付けの手動取込 |
| **リアルタイム代理閲覧** (監査者ログイン) | サーバーが復号・描画した帳簿を監査者がのぞく方式。平文非保持と両立しない | 非同期スナップショット送信 ([監査連携の移行ガイド](audit-migration.html)) |
| **パスキー専用モード** (`passkey_only_login`) | ログインパスワード = 常用鍵 (#385) と両立しない。全アカウントでパスワード必須化 | パスワードログイン + 任意の Passkey / TOTP 2 要素認証 |

### AI 証憑仕訳は引き続き利用できます

AI による証憑読み取り・仕訳提案は廃止されません。**処理経路がサーバー側からクライアント側へ
移行**しただけです。

- ブラウザ / `client-py` 上の orchestrator があなたの API キーで直接 LLM を呼び出します
- 対応プロバイダ: OpenAI / Google Gemini / Anthropic Claude / Ollama (ローカル)
- API キーを含む AI 設定もあなたの端末で暗号化して保存されます

## パスワードリセット (リカバリシード) (#385)

パスワードを忘れても、控えておいた **リカバリシード (24 単語)** で新しいパスワードを設定できます。
ログイン画面の「パスワードを忘れた」→ リカバリシードリセットから:

1. ユーザー名 + リカバリシード + 新しいパスワードを入力
2. ブラウザ内でシードから MK を復元し、新パスワードで再暗号化 (シードや新パスワードはサーバに
   送信されません)
3. **新しいリカバリシードが 1 回だけ表示**されます (古いシードは無効化。必ず控えてください)
4. 新しいパスワードでログイン

> リカバリシードは「全権復旧因子」です。シードを保有しているのは本人だけという前提のため、
> リセットすると (Passkey 専用にしていた場合でも) パスワード認証が有効になります。

## TOTP 2 要素認証 (任意) (#385 §3.6)

認証アプリ (Google Authenticator / Authy 等) の 6 桁コードをログイン時に追加で求める 2 要素認証を
**任意で**有効化できます (設定 → TOTP 2 要素認証)。パスワードが漏れても、その端末が無ければ
ログインできなくなります。

- **opt-in** (既定オフ)。有効化推奨
- **Passkey を設定済みなら TOTP は任意** (Passkey が第 2 要素を兼ねます)
- バックアップコード (10 個・1 回限り) を発行。認証アプリ端末を紛失したときの非常用
- リカバリシードでのパスワードリセット時は TOTP を再設定します
- 注: TOTP secret はサーバが検証時に復号する必要があるため、サーバ鍵で暗号化保管されます
  (帳簿データのような E2EE 対象ではなく、認証専用のシークレットです)

## よくある質問

**Q. ログインパスワードを忘れたら?**
リカバリシード (24 単語) で MK を復元し、新しいパスワードを再設定できます (上記
「パスワードリセット」)。リセット時にリカバリシードも新しいものに更新されます。

**Q. 端末を機種変更したら?**
新端末でいつものログインパスワードでログインすれば MK が解錠されます (Passkey 設定済みなら
Passkey でも可)。MK はラップ済みでサーバーに保管されているため、データはそのまま引き継がれます。

**Q. パスワードもリカバリシードも (Passkey も) すべて失ったら?**
**復元できません。** これは E2EE の性質上の制約です。リカバリシードのオフライン保管を
徹底してください。

**Q. 運営者に「データを見せて」と言われたら?**
運営者は鍵を持たないため、帳簿の内容 (摘要・取引内容・日付・**金額・科目コード**) や
証憑画像・医療費明細の平文を取り出すことはできません (上表の「暗号化される」項目)。
完全な開示が必要な場合は、あなた自身がエクスポートして提供する形になります。
