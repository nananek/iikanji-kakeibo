# v4.x → v5.0 移行ガイド — End-to-End 暗号化 (E2EE) への移行

v5.0 (Epic [#84](https://github.com/nananek/iikanji-kakeibo/issues/84)) で、いいかんじ™家計簿は
**End-to-End 暗号化 (E2EE)** に全面移行しました。サーバーは帳簿・証憑画像・医療費などの
**平文を一切持たなくなります**。暗号化・復号はすべてあなたの端末 (ブラウザ / `client-py`) 上で
行われ、サーバーには暗号文しか届きません。

本ガイドは、v4.x を利用してきた方が **何が変わり、何をすればよいか** を把握するためのものです。
監査連携 (税理士・公認会計士との共有) の移行は **[監査連携の移行ガイド](audit-migration.html)** を、
設計の詳細は **[v5.0 E2EE 設計書](index.html)** を参照してください。

> **実装状況 (2026-06)**: E2EE 化の実装は開発ブランチ上で完了しています。稼働中サービスへの
> 一斉移行 (メンテナンスウィンドウ・猶予期間) は E7 ([#114](https://github.com/nananek/iikanji-kakeibo/issues/114)) で別途告知されます。

---

## なぜ E2EE 化するのか

家計簿・帳簿は最も機微な個人情報の一つです。従来はサーバー運営者が技術的には
データの平文を閲覧できる構成でしたが、v5.0 ではその可能性そのものを排除します。
サーバー侵害・内部不正・法的開示要求のいずれが起きても、**鍵を持たないサーバーからは
平文が取り出せない**ことを設計で保証します。

---

## 何が暗号化されるのか

あなたの端末上でマスター鍵 (Master Key, MK) により暗号化され、サーバーには暗号文だけが
保存されます。

| 区分 | 内容 |
|------|------|
| **暗号化される** | 仕訳の摘要・日付・取引内容、医療費明細 (金額・患者名・病院名・治療内容・支払額・保険補填額)、証憑画像、AI 下書きの画像、残高キャッシュ、バックアップ |
| **暗号化されない (サーバーから見える)** | メールアドレス、勘定科目 (コード・名称・区分)、**仕訳明細の借方・貸方金額および科目コード**、AI 下書きの要約テキスト |

> **仕訳明細の金額・科目コードは平文メタとして残ります。** サーバー側で残高集計・
> 月次確定の損益振替を行うため、`journal_entry_lines` の `account_code` /
> `debit_amount` / `credit_amount` は平文列として保持されます (設計書 §12.3 / §15.6)。
> 一方、**何に使ったか (摘要・取引内容) や日付は暗号化**されるため、サーバーは
> 「ある科目にいくら計上されたか」は把握できても、個々の取引の中身は読めません。
> 勘定科目 (名称・区分) を平文で残すのも、ログイン不要の軽量 API
> (`client-py` のレポート集計など) を成立させるための同様の設計判断です。

---

## 鍵の仕組み — 3 つの認証要素

マスター鍵 (MK) は次の 3 つの要素それぞれでラップ (暗号化) して保管されます。
**どれか一つでも復元できれば** MK を取り戻せます。

1. **Passkey (パスキー)** — 端末の生体認証 / PIN。WebAuthn PRF 拡張から鍵を派生
2. **パスフレーズ** — Argon2id で鍵を派生。端末を問わずログイン可能
3. **リカバリシード** — BIP-39 24 単語。すべてを失ったときの最後の手段

> **重要:** サーバーは MK を持ちません。**3 要素をすべて失うと、暗号化されたデータは
> 誰にも (運営者にも) 復元できません。** リカバリシードは必ず紙等のオフラインで保管してください。

## 利用者がすべきこと

### 1. 鍵を設定する

v5.0 への移行後、初回ログイン時に鍵設定ウィザードが表示されます。

- Passkey を登録 (推奨) し、**パスフレーズ**と**リカバリシード**を必ず設定・保管してください
- 一斉移行のスケジュール (メンテナンスウィンドウ・猶予期間) は
  **E7 ([#114](https://github.com/nananek/iikanji-kakeibo/issues/114))** で告知されます

### 2. 必要ならデータをエクスポートしておく

E2EE 化後はサーバー側にデータの平文が残らないため、**鍵を失うと運営者による救済は
できません**。心配な場合は事前に手元へエクスポートできます。

- **Web**: `設定 → データエクスポート` から、復号済みの CSV + 証憑画像 + バックアップを
  zip でダウンロード (端末内で復号して生成)。メールでの受け取り (一時保存・有効期限つき) も可能
- **`client-py`**: `iikanji export` でローカル完結のエクスポート。証憑 200 枚 / 200 MB を超える
  大規模データはこちらを推奨

### 3. 廃止される機能を確認する (下記)

## v5.0 で廃止される機能とその理由

いずれも **「サーバーが平文を持つ」ことを前提とした機能**で、E2EE と本質的に両立しません。

| 廃止機能 | 理由 | 代替 |
|----------|------|------|
| **MCP サーバー** (`iikanji-mcp`) | LLM (Claude Desktop 等) に平文を渡す仕組みで E2EE 非両立。リポジトリは archive 化済 | `client-py` でローカルにエクスポート → 手動でアップロード |
| **Webhook 通知** (Discord 等) | 通知本文の生成にサーバー側で平文を読む必要がある | なし (将来 E2EE 整合的に再設計の可能性) |
| **自家ホスト LLM** (`llama_cpp` プロバイダ) | サーバー側で平文を LLM に渡す経路。E2EE では AI 処理はすべてクライアント側で実行 | クライアント側 AI (下記) |
| **自動取込** (auto_import) | サーバーが平文の明細を解析・自動仕訳する仕組み | CSV / OFX / Web 貼り付けの手動取込 |
| **リアルタイム代理閲覧** (監査者ログイン) | サーバーが復号・描画した帳簿を監査者がのぞく方式。平文非保持と両立しない | 非同期スナップショット送信 ([監査連携の移行ガイド](audit-migration.html)) |

### AI 証憑仕訳は引き続き利用できます

AI による証憑読み取り・仕訳提案は廃止されません。**処理経路がサーバー側からクライアント側へ
移行**しただけです。

- ブラウザ / `client-py` 上の orchestrator があなたの API キーで直接 LLM を呼び出します
- 対応プロバイダ: OpenAI / Google Gemini / Anthropic Claude / Ollama (ローカル)
- API キーを含む AI 設定もあなたの端末で暗号化して保存されます

## よくある質問

**Q. パスフレーズを忘れたら?**
リカバリシード (24 単語) で MK を復元し、新しいパスフレーズを再設定できます。

**Q. 端末を機種変更したら?**
新端末で Passkey を再登録するか、パスフレーズ / リカバリシードでログインしてください。
MK はラップ済みでサーバーに保管されているため、データはそのまま引き継がれます。

**Q. 3 要素をすべて失ったら?**
**復元できません。** これは E2EE の性質上の制約です。リカバリシードのオフライン保管を
徹底してください。

**Q. 運営者に「データを見せて」と言われたら?**
運営者は鍵を持たないため、帳簿の内容 (摘要・取引内容・日付) や証憑画像・医療費明細の
平文を取り出すことはできません (上表の「暗号化される」項目)。仕訳明細の金額・科目コードは
集計用の平文メタとして見える点に留意してください。完全な開示が必要な場合は、あなた自身が
エクスポートして提供する形になります。
